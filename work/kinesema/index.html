Engineering case study · Kinesema Labs

Engineering Kinesema.

Kinesema is a Deaf-first, inspectable language-technology system exploring how English can move through structured SgSL analysis and human review before any future signing motion. This page documents the engineering decisions behind that path—not a claim that the system is a completed translator.

The problem

The visible gloss is an intermediate layer, not the destination.

A text-only preview can easily look like a tool for learning gloss. Kinesema instead uses the visible structure as an inspection surface: reviewers can examine what the language stage proposed before that representation is allowed to influence future motion.

01

Different language structure

English input is analysed before a candidate SgSL structure is produced. The system does not treat word-for-word substitution as the final language result.

02

Inspect before rendering

Intermediate decisions remain visible so a human reviewer can inspect, question, and correct them before later stages turn language into motion.

03

Do not overclaim

Candidate structure is labelled as review-required. Motion, non-manual features, and final avatar output remain separate future layers.

What I built

A working vertical slice with explicit boundaries.

Inspectable language-analysis path

A deterministic analysis pipeline produces bounded candidate structure and surfaces intermediate decisions for review instead of hiding them behind an opaque response.

Python service boundary

FastAPI accepts bounded input, coordinates language analysis, validates the response shape, and returns only the fields intended for the inspection interface.

Review-aware interface

The product surface distinguishes submitted English, candidate SgSL structure, human-review status, and unavailable motion rather than presenting an intermediate artifact as final output.

Accessibility baseline

Semantic structure, keyboard access, visible focus, responsive layouts, and reduced-motion support are treated as implementation requirements, not a later visual polish step.

Engineering iteration

Simplifying the path improved reliability.

During integration, the request path became too complex and slow for an effective product experience. I reduced it to the smallest useful vertical slice, clarified each component's responsibility, and rebuilt validation and failure handling around observable needs.

  1. 01

    Preserve verified behaviour

    Start from the working language-analysis foundation and change only the boundary needed for integration.

  2. 02

    Simplify the request flow

    Use one bounded path from request through analysis to a validated response.

  3. 03

    Add protections from evidence

    Build failure handling around observed risks instead of speculative complexity.

  4. 04

    Match validation to the change

    Use focused tests for everyday work and broader checks at release or architecture milestones.

Current boundary

What the prototype does—and does not claim.

The current system is intentionally narrow. It is useful because its limits are visible, not because those limits are hidden behind a polished output.

NOW

Inspectable candidate structure

Short English inputs can be analysed and returned as candidate SgSL structure with explicit review status.

NEXT

Richer linguistic representation

Signer space, timing, non-manual information, and other motion-relevant language features need representations richer than gloss alone.

LATER

Motion and signing avatar

A reviewed linguistic representation can then inform a separate motion layer rather than sending raw English directly to an opaque renderer.
